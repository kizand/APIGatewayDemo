# API Gateway & Microservices Architecture Demo

Реализация отказоустойчивого, высокопроизводительного API Gateway (шлюза) на базе Spring Boot 4.1.x (Java 25) и чистого реактивного стека WebFlux. Проект демонстрирует централизованную маршрутизацию, динамическую модификацию заголовков, встроенную защиту от DDoS-атак и локальную JWT-аутентификацию/авторизацию.
Этот небольшой учебный проект демонстрирует централизованную маршрутизацию, динамическую модификацию заголовков и локальную JWT-аутентификацию/авторизацию пользователей по ролям без использования внешних провайдеров (Keycloak/Auth0).


## Архитектура системы

Проект реализован в виде многомодульного приложения:
• API Gateway (Порт: 8080) — единая точка входа. Направляет трафик, проверяет токены, добавляет системные заголовки.
• UserService (Порт: 8081) — блокирующий микросервис (Tomcat) для управления пользователями.
• OrderService (Порт: 8082) — блокирующий микросервис (Tomcat) для обработки заказов.


## Технологический стек

• Java 25 (Байт-код major version 69)
• Spring Boot 4.1.1
• Spring WebFlux (Асинхронный движок Netty для API Gateway)
• Spring Web MVC (для внутренних микросервисов)
• io.jsonwebtoken (jjwt) 0.12.5 (Локальная криптографическая проверка JWT)
• Spring Boot Actuator


## Реализованные сквозные функции (Cross-Cutting Concerns)

1. **Централизованная маршрутизация**: Запросы автоматически проксируются на основе путей: `/users/**` отправляются на порт 8081, `/orders/**` — на порт 8082.
2. **Модификация запросов (Фильтры)**: При пересылке запросов в `OrderService` шлюз на лету оборачивает и добавляет системный заголовок `X-Request-ID: 12345`.
3. **Локальная JWT-безопасность**: Валидация подписи токенов происходит прямо внутри шлюза по секретному ключу (алгоритм HMAC-SHA) без обращений к внешним серверам авторизации. Разделение прав:
   * Роль `USER` разрешает только `GET`-запросы на `/users/**`. Попытка сделать `POST` вернет статус **403 Forbidden**.
   * Роль `ADMIN` имеет полные права, включая выполнение `POST`-запросов на создание заказов.
4. **Глобальное логирование (WebFilter)**: Каждый проходящий сквозь шлюз запрос логируется в консоль приложения с указанием HTTP-метода и пути.
5. **Встроенный Rate Limiter (Token Bucket)**: Защита эндпоинтов от перегрузки реализована на базе атомарных счетчиков (`AtomicLong`) в оперативной памяти. При превышении лимитов (`burstCapacity: 20`, `replenishRate: 10`) шлюз мгновенно изолирует систему, возвращая клиенту статус **429 Too Many Requests**.


## Инструкция по запуску и тестированию в Postman

1. Генерация токенов

Для тестирования безопасности сгенерируйте токены на сайте jwt.io (алгоритм HS256):
• В поле Secret вставьте ключ: mySecretKeyForJwtAuthentication2026!!! (убедитесь, что галочка base64 выключена).
• В поле Payload для проверки пользователя вставьте:

{
"sub": "1234567890",
"name": "John Doe",
"role": "USER"
}

Для проверки администратора замените "role": "USER" на "role": "ADMIN". Скопируйте получившийся Encoded токен из левого окна.


2. Порядок запуска приложений в IntelliJ IDEA

Запустите класс ApiGatewayDemoApplication (модуль шлюза).
Запустите класс UserServiceApplication (порт 8081).
Запустите класс OrderServiceApplication (порт 8082).

3. Тестовые сценарии для Postman

Сценарий 1: Проверка аутентификации (Без токена)
• Запрос: GET http://localhost:8080/users/info
• Результат: HTTP 401 Unauthorized.

Сценарий 2: Успешный доступ пользователя к своим данным
• Запрос: GET http://localhost:8080/users/info
• Авторизация: Тип Bearer Token, вставьте токен USER.
• Результат: HTTP 200 OK. Текст: "Успех! Ответ напрямую из UserService..."

Сценарий 3: Попытка пользователя нарушить права доступа
• Запрос: POST http://localhost:8080/orders/create
• Авторизация: Тип Bearer Token, вставьте токен USER.
• Результат: HTTP 403 Forbidden.

Сценарий 4: Успешное создание заказа Администратором
• Запрос: POST http://localhost:8080/orders/create
• Авторизация: Тип Bearer Token, вставьте токен ADMIN.
• Результат: HTTP 200 OK. Текст: "Заказ успешно создан в OrderService... правами Администратора!"

Сценарий 5: Тест ограничения лимитов (Rate Limiting)
• Запрос: Любой эндпоинт (например, `GET http://localhost:8080/users/info`)
• Авторизация: Тип `Bearer Token` с валидным токеном
• Действие: Начните интенсивно и быстро (более 2-3 раз в секунду) нажимать кнопку **Send** в Postman.
• Результат: На 3-4 клик шлюз заблокирует отправку и вернет статус **429 Too Many Requests** с текстом *"Слишком много запросов! Пожалуйста, подождите."*
